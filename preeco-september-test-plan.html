A/B testing roadmap · September 2026

Every test on this roadmap attacks the same failure: Preeco asks high-ticket buyers to hunt for the information that closes the sale. Specs live twelve screens below the price. Delivery timing is invisible until you open a product. Alternatives arrive after three accordions. Offers are only reachable from the homepage. Four of the five tests move a decision input closer to the moment of decision — the fifth removes a step that no longer earns its place.

Batched by surface, not by priority. Each test runs for 14 days. Tests inside a batch touch different pages and report on different primary metrics, so they can run concurrently without sharing a denominator.

Batch A 7–20 Sep

Tests 01, 04 and 05 run together. They sit on three different surfaces — PDP purchase area, global navigation menu, collection grid — and each reports on its own primary metric, so no two compete for the same conversion event.

Batch B 21 Sep – 4 Oct

Tests 02 and 03 share the PDP but not the moment: 02 acts before add-to-cart, 03 only fires after a successful add-to-cart. Independent randomisation, plus a stratified read of 03's AOV guardrail by 02's bucket.

Why 01 and 03 never overlap

Both change behaviour around the same button. 01 changes what a shopper reads before pressing it, 03 changes where pressing it leads. Running them together makes an add-to-cart-rate lift uninterpretable, so they are deliberately split across batches.

Consistent bucketing

A visitor keeps the same variant for the full window across all live tests, keyed on a first-party visitor ID. Batch A's cross-surface interaction (04 and 05 change who reaches a PDP) is handled by reading 01 stratified by 04/05 bucket.

The five tests

Every test runs on all devices. Wireframes are drawn at 375 px because mobile is the tighter constraint; the desktop build follows the same logic in the wider layout. Dashed outlines mark what changes. Use the FI/EN switch in the header to flip the interface copy.

01

Benefits, Features and Specifications tabs

Batch A PDP · above the fold All devices Theme section + tab JS
Primary metric
Add-to-cart rate
Scope
All PDP sessions
Split
50 / 50
Duration
14 days

Problem

The purchase area carries five outcome-led bullets and nothing else. Everything a buyer needs to verify — the features narrative and the technical table — sits between roughly 2,100 px and 4,400 px further down the page. On a phone that is around twelve screen-heights away from the price and the add-to-cart button; on desktop it is still several full scrolls below the purchase column.

Someone checking whether a 60 cm working width clears their driveway has to abandon the decision area to find out, and the CTA leaves the viewport the moment they do.

Solution

A compact three-tab component sitting between the price block and the CTA:

  • Benefits — selected by default, holding the existing outcome-led bullets unchanged.
  • Features — the product's functional capabilities and what is included in the box.
  • Specifications — the decision-critical values only, in a two-column format.

Each panel is capped so the CTA stays visible. The full technical table stays where it is. All three labels fit on one line at 375 px without horizontal scroll. The selected state is a colour and a rule, not colour alone.

Hypothesis

If customers can switch between benefits, features and specifications without leaving the purchase area, add-to-cart rate will increase, because different shopper types can reach the information they need while staying next to the price and the CTA.

02

You might also like

Batch B PDP · below product details All devices Section + merchandising rules
Primary metric
PDP → PDP click-through
Scope
All PDP sessions
Split
50 / 50
Duration
14 days

Problem

The product details block ends and the next roughly 720 px is a Features accordion, a Delivery & payment accordion and a price-history chart before the first recommendation appears. That recommendation is a general behavioural feed, not a curated set of close alternatives.

A visitor who has just concluded this machine is too small has nothing comparable to click at the exact moment they conclude it. The rejection point and the alternative are separated by three collapsed sections.

Solution

A "You might also like" card row placed directly below the product details, before the accordions. Three to four genuinely comparable products from the same category, selected on use case, price band, key specifications and availability.

Each card carries the image, name, current price, verified rating, delivery message, one differentiating feature and a direct link to the PDP. Cross-category recommendations are explicitly excluded from this module — they already have a home further down.

Hypothesis

If customers see relevant alternatives immediately after evaluating the current product, PDP-to-PDP click-through and overall purchase conversion will increase, because visitors who reject the first option can continue toward a better-fitting product instead of leaving the site.

03

€300+ add-to-cart straight to checkout

Batch B PDP → cart → checkout All devices Redirect + eligibility logic
Primary metric
Checkout initiation rate
Scope
€300+ in-stock, no variant
Split
50 / 50
Duration
14 days

Problem

A €549,95 snow blower is a focused, single-product, single-variant decision. Nobody is building a basket. After the add-to-cart succeeds, the cart page adds a step whose only real job — reviewing a multi-item basket — does not apply.

What the extra step does supply is another chance to reconsider, another page to bounce from, and another render before the first checkout field appears.

Solution

For in-stock products priced at €300 or more, redirect to checkout immediately after a successful add-to-cart. Control keeps the current journey.

Existing cart contents are preserved, a clear route back to shopping stays visible on the checkout page, and any product still requiring a variant, configuration or other mandatory selection is excluded from eligibility.

Hypothesis

If customers who add a €300+ product are taken directly to checkout, checkout initiation and purchase conversion will increase, because one non-essential step is removed from a high-intent, high-ticket purchase journey.

04

Limited offers in the navigation menu

Batch A Global · navigation menu All devices Nav section + dynamic collection
Primary metric
Add-to-cart rate
Scope
Sessions that open the menu
Split
50 / 50
Duration
14 days

Problem

The navigation menu is a pure category index. Opening it is one of the strongest browsing signals a visitor gives, and Preeco answers it with ten links.

Meanwhile the most commercially important limited-time offers depend on homepage banners or category browsing to be found. Anyone who entered on a PDP, a search result, an ad or any other landing page can browse the whole session without ever seeing them.

Solution

A compact product-card module at the top of the menu — the drawer on mobile, the open nav panel on desktop — above the category links, populated from a dynamic "Limited offers" collection that is reviewed on a set cadence.

Two to four products in a horizontally scrollable row. Each card shows image, concise name, current price with a verified reference price, the saving, a genuine offer end date where one exists, and stock status. Expired and out-of-stock products drop out automatically. The category list stays immediately visible below the cards.

Hypothesis

If high-intent visitors see a small, current selection of limited offers when they open the menu, offer-PDP visits, add-to-cart rate and revenue per session will increase, because attractive deals become discoverable from every page without a return to the homepage.

05

Delivery estimate before the PDP

Batch A Collection · high-ticket All devices Card template + availability data
Primary metric
Collection → PDP click-through
Scope
Selected high-ticket collections
Split
50 / 50
Duration
14 days

Problem

For expensive, bulky, seasonal goods, delivery timing is a primary decision input — a snow blower that arrives after the first snowfall is the wrong snow blower. Preeco already computes and shows a precise estimate, but only once a PDP is open.

On a collection page a visitor can compare price, rating and specifications, and cannot compare the one variable that decides whether the product is usable this season.

Solution

Add a concise delivery estimate to every eligible product card on selected high-ticket collections, reusing the same availability and delivery data the PDP already uses. Plain language: "Estimated delivery in 4 days."

The message stays visually secondary to name and price, updates whenever the PDP estimate changes, and uses distinct wording for preorders, direct shipments, unavailable products and anything needing a location-specific freight calculation.

Hypothesis

If customers can compare estimated delivery timing directly on high-ticket product cards, qualified PDP visits and collection-to-purchase conversion will increase, because a major fulfilment uncertainty is resolved earlier in the shopping journey.
